Cause (re-review answer d): the kept request holds its CefBrowser (kept_browser_), which holds the browser's CefRequestContextImpl (browser_host_base.h request_context_), so the CefBrowserContext cannot shut down and is still registered in ImplManager::all_ at CefShutdown.
Prepared fix: engine/patches/0008 (this commit). The destruction observer stays registered for the CEF context after the browser is gone while requests are kept, so OnContextDestroyed reaches CancelKeptRequests, which releases the kept CefBrowser references. NOT BUILT, NOT PROVEN: the engine build needs the owner's go; the probe above must turn green (rc 0) with it. The release happens on the IO thread after a post from the UI thread, so whether it runs before the context set is checked at CefShutdown is unproven.
The patch re-applies on the base (git am onto 804d57968 files, checked). Delta of this change: see the report, section Fix round 2.

## 0008 pause and resume retries
engine/patches/0008 CefDownloadItemCallbackImpl::GiveUp logs an error when the 50 x 100 ms retries run out (DoPause and DoResume). CefDownloadItemCallback::Pause()/Resume() return nothing, so the embedder sees the failure as an unchanged item in its next OnDownloadUpdated; an error return would be an API change. Not built, not probed (no probe can make an item stay without a path).

## E15 item 3 (context destroyed with a kept request)
Unproven. README 0008 now says why: releasing the last CefRequestContext does not destroy a profile with a kept download (the kept request references the context), so CancelKeptRequests only runs at CefShutdown or proxy shutdown, where the process exits before a probe can see that no callback arrived. The promise in include/cef_resource_request_handler.h stays as the target.
