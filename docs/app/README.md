# Noche app self-tests (M1.1)

M1.1 is the window shell: frameless window, sidebar, toolbar and many tabs on our patched engine. The app checks the shell itself, without a person or a visible window. Recorded run: `docs/app/evidence/m1-1-run.txt`.

## Run

```sh
scripts/app-test.sh <check>...      # one or more of the checks below
scripts/app-test.sh --negative      # each check with its negative-control switch; exits 0 only if every expected-FAIL pair fails
```

`scripts/app-test.sh` builds `Noche.app` with the test hooks (`NOCHE_TESTHOOKS=1`), serves `Tests/fixtures/app` on a free localhost port and runs `Noche --selftest <check> --selftest-url <url>` once per check by direct exec. A check passes only if the app printed `pass`, exited 0 and never hit the shutdown watchdog. The profile is `~/Library/Application Support/Noche Test`, wiped before each check, never the dev profile.

Regression gate (the screen-lock state and load go in the evidence header): `swift test` (the XCTest summary line, "Executed N tests, with 0 failures", is what counts; the Swift Testing line above it reports 0 tests), `scripts/build-app.sh`, `scripts/smoke.sh build/Noche.app fixture` (0), `scripts/smoke.sh build/Noche.app closed-port` (2), `scripts/check-sandbox.sh build/Noche.app` (0), then every check. A plain `scripts/build-app.sh` carries no test code (`strings ... | grep -c NOCHE_TEST` is 0, and `nm build/Noche.app/Contents/MacOS/Noche | grep -c inTransactionHook` is 0). The `nm` proof has a positive control: the same `nm | grep -c inTransactionHook` on a `NOCHE_TESTHOOKS=1 scripts/build-app.sh` build must print at least 1, or a 0 on the plain build proves nothing.

## Hidden-run rules

- Every launch is hidden (`NCWindowModeHidden`): never `CefWindow::Show`, NSWindow alpha 0, ignores the mouse, floating level, ordered in with `orderWindow:NSWindowAbove relativeTo:0`, never key, never activates the app.
- Direct exec only: never `open`, never osascript, never system-level input. Input is synthesized `NSEvent`s handed to our own window and menu, or CDP.
- The script stops an app only by the one PID it started (TERM, then KILL after the app's own 40 s limit plus 20 s).
- Controls the app cannot give itself: new `Noche*.ips` crash reports (after a 3 s settle), the frontmost app (every 0.5 s, fails if it is ever Noche) and leftover helpers (polled up to 5 s).
- `exit-rc=2` is Chromium's own teardown watchdog (`content::RESULT_CODE_HUNG`, `_exit` after an engine shutdown that took over 10 s), seen only under heavy load (1-minute load 28 to 40 in Task 1; once in a full `--negative` run in Task 5, never in 10 runs of that pair alone at load 2 to 5). The check's own verdict is exit code 1, so a code 2 stays a failure of `--negative`; its fail line now carries the cause, the load and the engine's `Teardown watchdog` stderr line when there is one.
- A hidden window gets no frames while the screen is locked, and a loaded CPU can trip the watchdog: a timeout then is not necessarily a code fault. Check `ioreg -n Root -d1 | grep CGSSessionScreenIsLocked` and `uptime`.

## Two-phase checks and Chromium session restore (M1.2)

A check whose name ends in `-relaunch` runs twice on one profile: `--selftest <check> --selftest-phase 1` on a wiped profile, then `--selftest-phase 2` on what phase 1 left. Each phase prints its own `NOCHE_TEST <check> pass`, and the check passes only if both did (a failed phase 1 skips phase 2). The crash-report diff, leftover-helper poll, frontmost poll and stderr tail cover both phases. The harness argument is in `SelfTest.swift`, the checks in `SelfTestStore.swift`.

`chromium-restore-relaunch` and `chromium-restore-crash-relaunch`: phase 1 opens 3 fixture tabs and waits for their loads. The first then quits normally (the Quit path closes every tab one by one); the second prints `phase1-ready` and `scripts/app-test.sh` SIGKILLs the one app PID it started, so no shutdown runs. Between the phases the script prints the profile's session files (`NOCHE_TEST <check> info sessions=...`). Phase 2 waits until the engine tab and window counts have held still for 3 s (cap 15 s) after the first load, then counts engine tabs (`NCWindow.tabs`), NSWindows of the process and controllers, before Noche restores anything. It also fails if phase 1 left no profile. `--selftest-phase` with a value other than 1 or 2, or a `-relaunch` check without it, fails with `bad --selftest-phase`.

Result: Chromium's session service did write session files in both variants (normal quit: `Cache/Default/Sessions/Session_*` 7127 bytes and `Sessions_Encrypted/Session_*` 7855 bytes; kill: 6831 and 7295 bytes). Phase 2 then saw exactly 1 engine tab, 1 NSWindow and 1 controller in both. So after a normal quit and after a kill, with a session file on disk, Chromium's own restore adds no tabs or windows in our Chrome-style windows; no startup preference is set and no engine or bridge code changed. (Had it added tabs, the pref is `session.restore_on_startup` = 5, new tab page, from `chrome/common/pref_names.h` and `session_startup_pref.h`, set on the request context before the first browser.) Since M1.2 Task 3, between the phases `scripts/app-test.sh` runs `strings` on the newest unencrypted `Sessions/Session_*` and requires the 3 fixture URLs, and phase 2 expects 3 tabs because Noche restores them itself (a Chromium restore on top would give 6). Negative controls: both checks with `NOCHE_TEST_RESTORE_EXPECT=1` must fail with their own line.

Discarding (M1.6 Task 3b): a background tab not used for `discardAfterMinutes` (setting, default 120, B) is discarded by the engine (`CefBrowserHost::DiscardTab`, `WebContentsDiscard` on): it keeps its engine tab, `TabItem`, place and engine id (`TabItem.isDiscarded`, runtime only), draws dim like a dormant one (alpha 0.45), and a click reloads it in the same engine tab (never the dormant path, no second engine tab). The engine's own memory-pressure discards arrive through the same `OnTabDiscarded` callback and show the same way. Idle time runs from when a tab was last left (`leftAt`) or last selected, whichever is later. Never discarded: the active tab, a loading tab, a closing tab, or a tab playing unmuted audio or video (CDP query, `isPlayingMedia`). The question asks every frame of the page (M1.6 Task 7b): the page script walks the top document, open shadow roots and same-origin frames; then, when a frame is left, it attaches the child targets (`Target.setAutoAttach`, also inside each child session, so a cross-origin frame nested in an out-of-process one is reached), and on the top session and every child session reads `Page.getFrameTree` and asks each frame through its own isolated world (`Page.createIsolatedWorld`, `Runtime.evaluate` with `contextId`), which reaches a same-site cross-origin frame (one renderer process, no session of its own). A frame that is in a tree and got no answer, or does not answer within 3 s, makes the answer unknown and the tab is neither discarded nor (T7.2) archived. Whatever was attached is detached, awaited, before the question returns, and `discard()` runs after that (`discardSessions` in test builds reads 0). A child session id the engine no longer knows is written once to stderr (tab address and id), not on every question. Known limits: a page sounding only through Web Audio is not seen as playing; The media question asks without user activation and gives up after 3 s (a hung page is not discarded). A restore is not a use of a tab (it keeps its saved stamp), so after a long break every restored background tab is discarded about 60 s after launch. Option A (Memory Saver prefs) is not used.
Known limits: the loading arc does not spin.

A window restored from a saved frame narrower than 487 pt opens 487 pt wide (the left edge kept).

Pinned and dormant tabs (M1.6 Task 3): a pinned tab is a list item that may have no engine tab (`engineID` nil, drawn at alpha 0.45). Cmd+W, the close button or the page closing a pinned tab makes it dormant at its pinned page (its place and id stay; it is not on the closed list); a click, Cmd+1 to 9 or Next and Previous Tab give it a new engine tab at `pinnedURL` and select it. The window always keeps one engine tab: when the last one would close or go dormant (a pinned one, or any when dormant tabs exist), a blank day tab opens first. A restore creates engine tabs for the unpinned tabs and the selected tab, pinned or not; the other pins come back dormant, so 12 pins cost nothing until clicked. A restore whose tabs do not all arrive within 15 s applies the saved structure to the ones that did and keeps the missing ones as dormant tabs. Known limits: back and forward history, scroll and form state are lost on a dormant round trip (note 3.2, option C); a dormant tile after a relaunch shows its icon once the saved icon address has been fetched (one request per dormant tile at launch, no cookies, 5 s, http and https only, 1 MB; the globe until then or when it fails); Close All Tabs still closes pinned tabs (they go dormant) until Task 7 makes it close day tabs only. Next and Previous Tab (Shift+Cmd+] and [) step through the visual order with pins included and wake every dormant tab they land on (the spec, section 2, gives the order only and says nothing about dormant tabs; so they are not skipped, which keeps the key from silently jumping over a row). A close the engine or a page starts on the window's last tab closes the window before Noche hears of it (CEF calls neither `DoClose` nor a veto the host can use; `CanClose` comes too late for a new tab), so the window is made again (flicker of one frame, same frame and id); a saved structure the list refuses (duplicate ids) keeps every saved tab dormant in the current list and writes a NOCHE restore line to stderr.

Drag and drop (M1.6 Task 5, notes 2.1 and 4.1): a press on a tab row, a grid tile or a group row that moves 3 pt starts a drag (the press still selects a tab at once; a group row now toggles on the release, so a drag does not open or close it). The drag carries `{"kind", "id", "window"}` as JSON on the pasteboard type `app.noche.sidebar-item`, an image of the row at alpha 0.9, and is a move inside the application only. `SidebarDocumentView` is the destination: `DropResolver.resolve` (pure, NocheCore) turns the pointer and the dragged item into a `DropTarget` and an indicator, and a drop is one `TabList.move(_:to:)` or `moveGroup(_:to:)` through `BrowserWindowController.performDrop(_:to:)`. Rules: the grid area (down to the 3 pt gap under its last row) takes a tab at the slot nearest the pointer (41 x 41 ghost; a group is refused); in the persistent area and the day list a loose row takes the pointer's half (above the middle: before it), a folder row its quarters (top: before, middle: joins at its end, outlined; bottom: after a closed folder, or the first place inside an open one, builder call, because the line would sit inside its box); below the middle of an open folder's header the pointer is on its children and the drop joins at that position; below the last child's box a drop leaves the folder. A group dragged takes the same quarters and the halves of loose rows, and is refused in the middle of a folder, over its children and on the grid; it moves with its tabs and is pinned or unpinned by the area it lands in. A tab dragged out of an open folder and dropped on its own row (or its folder's last row) stays in the folder at its place, with the line inside the folder's box. A tab dropped in the persistent area is pinned as a loose row, under the divider unpinned (a dormant pinned tile unpinned this way, or by Unpin, is an unpinned row with no engine tab: its close button and its menu's Close remove it from the list and the store and put it on the reopen list; a pinned dormant tile still has Close disabled). A payload that names a tab or group not in the window's list gets no operation and no indicator. Hovering the middle of a closed folder for 0.6 s opens it; it closes again at the end of the drag unless the tab joined it. The list scrolls while the pointer is within 24 pt of its top or bottom. The dragged row keeps its view for the whole drag and counts inside the 40 row views of ruling M72 (the realized row farthest from it gives up its view); the drop indicator is raised above every row realized while it shows. The slot a drag starts from is the row's own slot (a drop on it changes nothing), so a first move straight to another slot taps once. Same window only: a payload that names another window is refused. A drag that ends with no operation (Escape, a drop outside) changes nothing and the row slides back. Known limit: with no pinned tab there is no grid area to drop on (the first tile comes from Pin; a drop in the persistent area pins a loose row). The real `NSDraggingSession` (the system's image, Escape, the slide back, the periodic updates while the pointer rests) cannot run on synthesized events: owner check 25.
Move to Window and Merge All Windows (M1.6 Task 5b, ruling M97): Tabs > Move to Window moves the active tab and the group menu's Move to Window the group. Reopen Closed Tab never brings a moved tab back; both windows are saved at once, the destination first (the group row goes before its tabs in the same write; the source's save then tombstones only what it still names). - With no pinned items and no groups the divider sits at y 60 (6 pt under the list top, 54), the New Tab row at 65 and the day tabs from 104 (M1.6: the New Tab row is below the divider, table 1.1).

## M1.5 bridge: downloads, permission requests, quit pause

`NCDownloads` (`Sources/CefBridge/NCDownloads.mm`) is one object per process over the global request context. Downloads with a tab report to the window client's download handler, downloads without one (the tab closed, restored from history) to the profile handler `CefRequestContext::SetDownloadHandler` (engine patch 0008, installed by `start(observer:)`); both end in the same `NCDownloadItem` updates, delivered to the observer on a later main-queue turn. Noche never answers `OnBeforeDownload`: Chromium's target determiner picks the file name (" (1)" suffix included) and folder, with no save dialog. The folder is the profile preference `download.default_directory`, set at startup to `~/Downloads` through `+[NCEngine setDownloadDirectory:error:]` (ruling E12: a download with no browser keeps Chrome's default directory); M1.8 Settings will call the same method with a user choice. `suggestedName` is the name Chromium suggested before the download began, and the final file's name once it is complete (the engine's own suggested name is the `.crdownload` intermediate). `pauseAllForQuit()` runs first in `beginShutdown`: it asks the engine to pause every download in progress, and a paused download survives the clean quit (engine patch 0008 with `KeepPausedDownloadsAtShutdown`) and comes back resumable. The pause is applied asynchronously by the engine: the quit waits for the paused updates (3 s at most) before it closes the windows (M1.5 task 3, `DownloadsController.pauseAllForQuit`). The bridge drops a download's name note once it completes or is canceled, and a download restored after a quit reads as paused (the engine reports it interrupted and paused), named after its address's last path component.

`NCWindowDelegate window:tab:requestsPermissions:origin:decide:` is optional. It covers `OnRequestMediaAccessPermission` (camera and microphone; deny cancels the request) and `OnShowPermissionPrompt` (everything else; `OnDismissPermissionPrompt` retires the prompt, so a late `decide` does nothing). `decide(allow, remember)`: allow accepts, deny with remember is Chromium's deny (the page sees `denied` and the choice is kept), deny without remember is a one-time dismiss. The mask names camera, microphone, geolocation and notifications; any other kind sets `Other`. `origin` has no trailing slash. A delegate that does not implement it leaves Chromium's own prompt, which is what the production controller does until the prompt card (Task 4) exists.

## M1.5 Downloads window and sidebar button

Cancel on a download restored after a quit (paused or interrupted) works like Cancel on a running one: the engine cancels it (engine patch 0011, CEF 156.0.19-noche.3664+g02b0496, the engine the app needs), its canceled update ends the row as Canceled with Remove, and its partial file is deleted. An engine without that patch stays silent for a restored item, so `DownloadsController.cancel` keeps a fallback: after `cancelGrace` (2 s) a row still paused or interrupted is given up like a removed one (stored in `downloadsRemoved`; a row in progress is never given up).
`DownloadsController` (`Sources/Noche/DownloadsController.swift`) is the observer of `NCDownloads`; the app calls `start(observer:)` once at startup, after the engine started and before any window or session is restored, so downloads whose tab closed and downloads restored from the last session reach it too. It keeps the items newest first and posts `DownloadsController.changed` on every update. `DownloadsWindowController` (`DownloadsWindow.swift`) is the native window behind Window > Downloads (Shift+Cmd+J) and the sidebar button: a titled window with one `DownloadRowView` per download (name, "n MB of m MB (p%)" or "Complete - size" or "Paused - ..." or "Canceled", a progress bar while unfinished, and the buttons that fit the state: Pause or Resume and Cancel while unfinished, Open and Show in Finder when complete). The quit pauses what runs and waits for the paused updates (3 s at most) before it closes the windows, so a paused download survives it and comes back resumable. Resume across a clean quit needs a strong validator (ETag or Last-Modified over HTTP/1.1); without one Chromium restarts the download, as stock Chrome does.

Builder calls (no capture of a Downloads window or of the ring exists): the window is 560 by 460 pt with the card fill and the command bar's text tokens (`ChromeStyle`); the sidebar button is live-ui.md section 3 (bottom row, icon 14, `#666`) at the reference's x 14 and 42 pt above the window's bottom, widened from 18 to 36 pt so a ring fits around the icon; the ring is a 2 pt circle of radius 11.5 pt (a `#E0E0E0` arc from 12 o'clock over a 15 percent white track, bytes received over bytes expected of all unfinished downloads together, an empty track when no total is known) shown while any download is running or paused and gone when none is; the scrolling tab list ends above the 42 pt bottom row. Open and Show in Finder call `NSWorkspace.open` and `activateFileViewerSelecting`; a test build records the call in `DownloadsController.workspaceLog` and never makes it.

## M1.5 Site permission prompts

`BrowserWindowController+Permissions.swift` implements the bridge's permission method, so Chromium's own bubble never shows.
