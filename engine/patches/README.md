# Patches

Noche's engine patches are `git format-patch` output against the pinned CEF commit (see `engine/README.md`). `engine/build.sh patch` applies them with `git am --3way` in name order, so prefix names with a number (`0001-...`).

Changes to Chromium itself go in as new files under CEF's `patch/patches/` plus an entry in `patch/patch.cfg`, all inside a Noche patch. CEF's own patcher then applies them during `build`.

To regenerate a series: commit on the `noche` branch in `chromium/src/cef`, then `git format-patch <pinned commit>`.

`engine/build.sh patch` resets `src/cef` with `checkout -f -B noche`, which loses uncommitted edits, so commit on `noche` and run `git format-patch` before re-running `patch`.

CEF's patcher applies `cef/patch/patches/*.patch` to Chromium in place, and `engine/build.sh patch` only resets `src/cef`, so Chromium keeps those edits. Before dropping or editing a Chromium-side patch, revert it in Chromium with CEF's `tools/patch_updater.py` (its `--revert` option, optionally limited with `--patch <name>`), from `chromium/src/cef`: `python3 tools/patch_updater.py --revert --patch <name>`.

`engine/build.sh patch` also restores (git checkout) the Chromium files of any Chromium-side patch file the series adds or changes that applies neither forward nor backward to the current Chromium tree, so an amended patch re-applies over its old form. A patch already applied in its new form is left alone. `engine/test.sh` covers this with a fixture.

The series is experimental-API only. The CEF-side parts of popups-as-tabs engage only when `CEF_API_IS_ADDED(CEF_EXPERIMENTAL)`, but the Chromium-side hunks (tabs allowed in a views-hosted Browser, window type reported as normal, installs anchored to the CEF window) apply to every views-hosted Chrome style Browser regardless of `CEF_API_VERSION`. Do not ship the series to a client that pins a stable API version.

0006 closes the teardown window: from the moment the last tab's WebContents is gone (before `OnBeforeClose` and `OnBrowserDestroyed`), `GetTabs`, `GetActiveTab` and `GetTabCount` report only live tabs, and `AddTab` and the extension action calls refuse. Probe check: `close-callbacks`.

0007 stops the zoom bubble in views-hosted browsers: `ZoomViewController::UpdateBubbleVisibility` returns early when the Browser is a CEF views-hosted Browser (`cef_delegate()->IsViewsHosted()`), so zoom steps no longer order a bubble window in at the top-left of the window. Zoom itself is untouched (per-host levels, `GetZoomLevel`, the zoom commands all work). The change is a Chromium-side patch file (`chrome_browser_ui_zoom_bubble.patch`) listed in `patch/patch.cfg`. Probe check: `zoom-no-bubble`.

0008 keeps downloads alive without a tab. CEF side: the resource request wrapper no longer cancels (`ERR_ABORTED`) an in-flight request whose network response already arrived when only its browser is destroyed (context destruction still cancels everything), because a download that took over a navigation owns that request and must outlive the tab. Such a kept request is not reported to the client's resource handler as aborted; its one completion arrives when the download's request finishes, with the original browser and frame (`IsValid()` false by then), and a kept request cancelled with its request context gets none. `CefRequestContext::SetDownloadHandler` (experimental) sets a profile level `CefDownloadHandler`; `OnDownloadUpdated` now takes a NULL browser (`optional_param=browser`) for items without a live browser, existing items are replayed when the handler is set, and items restored from history are kept (observed, announced) instead of cancelled at creation; when such an item resumes with no browser, `DetermineDownloadTarget` keeps its recorded target and intermediate path (and its recorded danger type) instead of letting Chrome pick a new name in the default directory. The pause and resume retry loops are bounded. Chromium side, two new patch files listed in `patch/patch.cfg`: `content_download_keep_paused.patch` adds `download::features::kKeepPausedDownloadsAtShutdown` (off by default, embedders turn it on with `--enable-features=KeepPausedDownloadsAtShutdown`) so `DownloadManagerImpl::Shutdown` interrupts a paused download with reason CRASH and keeps its partial file instead of cancelling it (it then restores as resumable, like crash recovery); `chrome_browser_ui_tab_group_feedback_guard.patch` makes `SharedTabGroupFeedbackController::TearDown` stop observing the tab group sync service and `MaybeShowFeedbackActionInToolbar` return when its Browser is gone (early-quit crash), which makes the `DataSharing` flags optional. The pause and resume retries now log an error when they give up (`CefDownloadItemCallback::Pause()/Resume() gave up for download <id>`) and call `DownloadItem::UpdateObservers()`, so the embedder gets one more `OnDownloadUpdated` that still reports the item not paused after `Pause()` (or still paused after `Resume()`); the callbacks return nothing, so that unchanged state is the only signal without an API change. Kept state release: a kept request holds its `CefBrowser` (a `KeptRefs` object shared with the destruction observer), and with it the browser's request context. `CefBrowserHostBase` is plainly reference counted, so the last kept reference is always dropped on the UI thread (`KeptRefs::DropOnUIThread`, posted with `CEF_POST_TASK` to `CEF_UIT`, `cef/libcef/browser/thread_util.h:53` and `:17`). The destruction observer stays registered for the CEF context after its browser is gone while requests are kept, and `OnContextDestroyed` drops the kept references synchronously on the UI thread inside `CefContext::ShutdownOnUIThread`, before `CefShutdown` returns, which lets the last `CefRequestContextImpl` be deleted there (`DeleteOnUIThread` deletes inline on the UI thread) and `CefBrowserContext::Shutdown` unregister the context before the `ImplManager` destructor checks `all_` at exit. Nothing is kept once `CefShutdown` has started (`CONTEXT_STATE_VALID()` is false while `DestroyAllBrowsers` destroys the browsers), so a download running in an open tab at quit is cancelled as before. When the last kept request completes the references are dropped too, again on the UI thread. `CancelKeptRequests` is a separate path that runs when the proxies shut down, not at context destruction. A kept request that completes after `OnContextDestroyed` dropped the references reports `OnResourceLoadComplete` with a NULL browser and frame, which the header allows (`optional_param=browser,optional_param=frame`, `cef/include/cef_resource_request_handler.h:170` and `:191` in the engine tree, `:167` and `:188` in the distrib copy). Until then a profile whose window closed during a kept download stays loaded on purpose: the download owns the request, as Chrome keeps the profile alive for a running download (`ScopedProfileKeepAlive`, `chrome/browser/download/download_status_updater.cc:174`). The first amended patch was inert (its observer used a WeakPtr that `OnDestroyed` had invalidated); this one does not depend on it. Not built yet: probe `download-keep-quit` is the test (expected red on the engine without this patch: rc 134 and `DCHECK failed: all_.empty()` at `browser_context.cc:45`), and `download-keep-quit-control` (the download finishes before the window closes) passes on both. Unproven promise: "a kept request cancelled with its request context gets no completion" has no probe. `CancelKeptRequests` runs only when the proxies shut down, where the process exits before a probe can observe that no callback arrived, and context destruction itself drops the kept references instead of cancelling (the request then completes with a NULL browser); the promise stays as the target. Probe checks: `download-tab-close`, `download-restart-crash`, `download-restart-1` and `download-restart-2`.

0009 lets the embedder discard a background tab. `CefBrowserHost::DiscardTab()` (experimental) goes through Chromium's own entry, `TabLifecycleUnitSource::GetTabLifecycleUnitExternal(web_contents)->DiscardTab(EXTERNAL)`, and refuses the active tab and any discard while `WebContentsDiscard` is off (with the feature off Chromium replaces the WebContents, which destroys the CefBrowser; embedders turn it on with `--enable-features=WebContentsDiscard`), and returns false for a browser that is not Chrome-style. `CefDisplayHandler::OnTabDiscarded(browser, discarded)` (experimental) reports every transition into and out of the discarded state, including Chromium's own automatic discards; `OnLoadEnd` also fires at discard time, so it is not a discard signal. CEF side only. Probe checks: `discard-p1`, `discard-p1b`, `discard-p2`, `discard-p3`.

0010 clears one profile's browsing data. `CefRequestContext::ClearBrowsingData(remove_mask, since, callback)` (experimental) runs the profile's own `content::BrowsingDataRemover` from `since` to now (a zero `since` means all time) with a mask of cookies, cache, site storage (local storage, IndexedDB, service workers, Cache Storage), history, downloads, form data and passwords; the Chrome-layer types act through the profile's `ChromeBrowsingDataRemoverDelegate`. Callable from any thread; the callback runs exactly once, asynchronously, on the UI thread; it does not run if the context never initializes, and during profile teardown it can arrive after teardown began (the removal did not complete). Each request context has its own remover, so clearing one profile never touches another. CEF side only. Probe checks: `profile-clear` and the other `profile-*` checks.

0011 makes Cancel work on a restored interrupted download. A download paused at quit comes back on the next launch as INTERRUPTED (0008); `CefDownloadItemCallback::Cancel()` used to cancel only IN_PROGRESS items (`DoCancel` in `libcef/browser/download_manager_delegate_impl.cc`), so Cancel on a restored row left the partial file and sent no update. It now also cancels an INTERRUPTED item: `DownloadItemImpl::Cancel(true)` takes it to CANCELLED, deletes the partial file (`download_item_impl.cc` `InterruptWithPartialState`, the `INTERRUPTED_INTERNAL` case) and notifies observers. A completed or already cancelled item is left alone. CEF side only, comment-only change to the `Cancel()` doc, no API change. Probe checks: `download-restored-cancel-1` and `-2` (run 1 then 2) and the control `download-cancel-complete`.
